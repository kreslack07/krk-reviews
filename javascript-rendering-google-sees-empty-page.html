Why Google May See an Empty Page: JavaScript Rendering and the Fix Order

Published 2026-11-25 · By KRK Digital Products (ABN 71 770 320 895, Australia)

If your site is built as a React, Vue, Angular or plain JavaScript app, there are two versions of every page: the one you see in a browser, and the one Google may see. They are not always the same document. Google does run JavaScript — it renders with “an evergreen version of Chromium” — but rendering sits on its own queue, and that queue is why a page can be crawled, reported as fine, and still contain almost nothing Google can index.

The three phases, and where pages wait

Google Search processes JavaScript in three phases: crawling, rendering, indexing. Googlebot queues pages for both crawling and rendering, and in Google's own words, “it is not immediately obvious when a page is waiting for crawling and when it is waiting for rendering.”

Googlebot queues all pages with a 200 status code for rendering, unless a robots meta tag or header tells Google not to index the page. The page may stay on that queue “for a few seconds, but it can take longer than that”. Only once Google's resources allow does a headless Chromium render the page, execute the JavaScript, and hand the rendered HTML back for indexing.

So a JavaScript page is rarely broken. It is late. And two kinds of visitor never reach the render queue at all: anything blocked in robots.txt, because Google Search “won't render JavaScript from blocked files or on blocked pages”, and every bot that cannot execute JavaScript in the first place.

The check that settles it in two minutes

Do not reason about it — look at the rendered HTML. If your body copy, prices, headings and links are missing from it, Google is indexing an empty shell.

  • Search Console → URL Inspection → View crawled page → HTML. This is the document Google indexed, not the one your framework produced.
  • Rich Results Test shows the same rendered HTML for a staging or live URL before you ship.
  • View source on the raw server response with the browser cache disabled. If content only appears after scripts run, the server is sending an empty shell.

Fix order

Ranked by how much of the page each fix recovers:

  1. Serve the money pages as HTML. Server-side render or pre-render services, pricing, location and product pages. Google recommends this outright because it makes a site faster for users and crawlers, and because “not all bots can run JavaScript”.
  2. Put the primary copy in the initial HTML — titles, headings, the paragraph that answers the query, and prices.
  3. Use real links. Google “can only discover your links if they are <a> HTML elements with an href attribute”. Hash-fragment routing such as #/services cannot be reliably resolved, so client-side routing belongs on the History API.
  4. Keep the canonical in the original HTML rather than injecting it, and never let JavaScript point the canonical at a different URL than the HTML did.
  5. Answer missing pages with a real status code. In single-page apps, either redirect to a URL the server answers with 404, or add a noindex meta tag to the error view. Otherwise you generate soft 404s.
  6. Check web components. Google flattens shadow DOM and light DOM into the rendered HTML, and content that is not in that rendered HTML cannot be indexed.

Lazy-loaded images, long-lived caching and content fingerprinting matter as well — but only after the content itself is visible to a crawler. Do them last.
