Mobile-First Indexing: Which Version of Your Site Google Actually Reads

Published 2026-11-21 · By KRK Digital Products (ABN 71 770 320 895, Australia)

There is a version of your website that Google reads, and on most sites it is not the one you see on a laptop. Google's documentation states it plainly: Google uses the mobile version of a site's content, crawled with the smartphone agent, for indexing and ranking. That is mobile-first indexing. Every service page, price and opening hour has to exist on the small screen, or it effectively does not exist in Search.

The three configurations, and the one that ends the problem

Google's guide recognises three ways to serve mobile users:

  • Responsive design — one HTML response at one URL for every device, laid out per screen size. Google recommends it as the easiest pattern to implement and maintain, and it removes this class of problem: content and metadata are identical by construction.
  • Dynamic serving — one URL, different HTML per device, chosen by user-agent sniffing and a Vary: user-agent header.
  • Separate URLs — an m-dot host with its own HTML.

The parity rules below apply to the second and third. If you are unsure which you run, view source on a phone and on a desktop: different markup at the same URL means dynamic serving, a different hostname means separate URLs.

Where parity breaks, and the fix

  • Robots meta tags. Keep the same robots tag on both versions. A noindex or nofollow that appears only on mobile can keep the page out of Google entirely — the most expensive version of this bug, because the desktop copy looks healthy.
  • Lazy-loaded primary content. Google will not load content that needs a swipe, click or keystroke to appear. If the body copy or price table only renders after user interaction, Google may never see it.
  • Content and headings. Accordions or tabs are fine on mobile, but the content inside must be equivalent to desktop with the same clear headings. Indexing comes from the mobile version, so copy trimmed for mobile is copy trimmed from the index.
  • Structured data. Local business, Product and Breadcrumb markup belongs on both versions, with URLs matching the version it sits on.
  • Title and meta description. Equivalent on both versions.
  • Images. Same descriptive alt text, same quality, supported formats, and no URLs that change on every page load.
  • Blocked resources. If the mobile page pulls CSS, JavaScript or images from a path disallowed in robots.txt, Google cannot render it properly.

Extra checks if you run an m-dot site

Four more documented failures: a mobile URL serving an error status while the desktop URL works, so the page drops from the index; indexable desktop URLs that all redirect to the mobile home page, which vanish too; URL fragments starting with #, generally not indexable; and hreflang links crossing from mobile to desktop versions, which must stay within their own version.

How to confirm it on your own site

Search Console's URL Inspection reports which crawler fetched the page in its live test, so you can watch the smartphone agent pull your URL and read the rendered HTML it received. Compare that with what a customer on a phone sees, and with the desktop version — where the three disagree, you have found the gap.
