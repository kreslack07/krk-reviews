Core Web Vitals for Small-Business Websites: A Practical Fix Order (LCP, INP, CLS)

Published 2026-11-21 · By KRK Digital Products (ABN 71 770 320 895, Australia)

Most small-business sites are not slow because of anything mysterious. They are slow because a hero image is being served at desktop resolution to a phone on 4G, because seven third-party scripts load before any paragraph renders, or because a chat widget drops into the page after the layout has settled. Each of those has a name, a number attached to it, and a fix that a site builder or a developer can apply in an afternoon.

This is the Core Web Vitals check from our 48-hour AI & SEO website audit, written out in full so you can run it yourself. If your site already measures well, good — you have saved yourself a job. If it does not, you will know which file to open.

The three metrics, and the numbers Google publishes

Core Web Vitals are field measurements: they describe what real visitors experienced, not what a test rig saw once. Google's published thresholds, documented at web.dev/articles/vitals, are:

  • LCP (Largest Contentful Paint) — loading. Good is 2.5 seconds or less; poor is over 4 seconds. Detail: web.dev/articles/lcp.
  • INP (Interaction to Next Paint) — responsiveness. Good is 200 milliseconds or less; poor is over 500 milliseconds. Detail: web.dev/articles/inp.
  • CLS (Cumulative Layout Shift) — visual stability. Good is 0.1 or less; poor is over 0.25. Detail: web.dev/articles/cls.

Google applies those thresholds at the 75th percentile of page loads, reported separately for mobile and desktop — see how the thresholds were chosen. That part is easy to skip: it means three visits in four have to fall inside the threshold. One visitor on a slow phone does not move your number on its own, and a fast laptop does not rescue it either.

INP replaced the previous responsiveness metric, FID, which older guides still name. Advice written to optimise FID is out of date.

Field data versus lab data — do not confuse them

Two tools, two different things:

  • PageSpeed Insights reports both. The upper section is field data — real traffic from real devices, the same data that feeds the thresholds above. The bottom section is a Lighthouse lab test: one synthetic load from a Google server. The lab score is a diagnostic, not your grade.
  • Search Console → Core Web Vitals groups your URLs into good, needs improvement and poor, based on field data, per device class.

A perfect Lighthouse score with failing field data is common and it is not a contradiction: the lab test is a clean room, your visitors are not. Fix what the field data shows. Use the lab report to find out why.

LCP: what to fix

LCP is the point at which the element occupying the bulk of the viewport — typically a hero image, a heading or a video poster — has finished painting. Three causes cover most small-business sites:

  1. The hero image is too heavy. A 4000-pixel-wide JPEG rendered into a 1200-pixel box is being paid for twice: once in download size, once in decode time. Serve it at the size it is displayed, use WebP or AVIF, and use srcset so phones get a smaller file than desktop screens. Where you control markup, preload the hero with <link rel="preload" as="image"> so it is fetched before the browser discovers it in the layout.
  2. Render-blocking CSS and fonts. Stylesheets and web fonts in the <head> hold back the initial paint. Load fonts with font-display: swap and a preconnect to the font host, and keep unused CSS out of the critical path. If a builder plugin offers "optimise CSS delivery" or "defer non-critical CSS", that is this fix.
  3. Server and redirect latency. Every redirect hop before the HTML arrives is time on the clock. A site that bounces visitors through http to https, then to another hostname, then to the canonical path, adds hundreds of milliseconds before a single byte of content is parsed. Collapse the chain to one permanent redirect.

If the LCP element is injected by JavaScript, the honest fix is to render it in the HTML instead — lazily loading an above-the-fold image is a common own goal, because lazy loading defers exactly the element the metric is waiting for.

INP: the third-party tax

INP measures how long the page takes to visibly respond after a visitor taps or types. In practice it is a long-task problem: the main thread is busy running someone else's JavaScript when your visitor asks for something.

The usual suspects on a small-business site are chat widgets, marketing and heatmap trackers, social embeds, and a tag manager loaded with pixels. You usually cannot delete them, so do the next best things:

  • Load non-essential third parties with async or defer, or after the visitor interacts, rather than synchronously in the head.
  • Load widgets on the pages that need them — a chat widget does not need to initialise on a legal page nobody scrolls.
  • Audit the tag manager once a quarter. Every tag added for a campaign tends to outlive the campaign.
  • Break long tasks up: a single script that blocks the main thread for half a second is one blocked tap.

When INP is poor, the useful question is what ran on the main thread in the second before the visitor interacted, and your browser's performance profiler will answer it.

CLS: reserve the space

CLS scores how much visible content jumps around while a visitor is reading. It is the easiest of the three to fix, because the fix is usually the same: reserve the space before the content arrives.

  • Give every image and video explicit width and height, or an aspect-ratio box. A browser that knows the dimensions can hold the space.
  • Reserve fixed space for ads, cookie bars, banners and inline embeds. A consent banner that pushes the whole page down after 800 milliseconds is a layout shift by definition.
  • Use font-display: swap with a fallback metric-matched font so the swap does not reflow the text block.
  • Avoid inserting content above what a visitor is already reading — "related posts" pushed above the fold after load is the classic example.

Fix them in this order

  1. Measure. Open PageSpeed Insights on five landing pages and note which metrics fail in the field data section, per device.
  2. Start with LCP. It is the metric visitors feel, it is usually one or two images, and it is a relatively cheap fix.
  3. Then INP. Move third parties off the critical path, then remove the ones nobody uses.
  4. Then CLS. Dimension every image and reserve every dynamic slot.
  5. Re-measure after a week. Field data is a rolling window of real visits, so it moves slowly. Give it time before you judge a change.

Do not rebuild your site to chase a perfect score in a lab tool. The three numbers that matter are LCP, INP and CLS in the field, on mobile, at the 75th percentile.

What a manual check will not tell you

A self-check tells you that LCP is failing in field data. It does not tell you which of six images, which of two font hosts, or which of the eleven scripts in your tag manager is responsible, and it will not write the replacement markup for you.
