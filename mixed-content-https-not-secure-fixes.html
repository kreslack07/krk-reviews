Mixed Content: Why Chrome Still Labels an HTTPS Site “Not Secure”

Published 2026-11-26 · By KRK Digital Products (ABN 71 770 320 895, Australia)

You bought the certificate, the padlock is on the address bar, and Chrome still flags the page as not secure. In most cases the cause is mixed content: the HTML itself arrived over HTTPS, but something inside the page — an image, a font, a script, an embedded map — was requested over plain HTTP.

What mixed content actually is

web.dev defines a page as mixed content “when its initial HTML is loaded over a secure HTTPS connection, but other resources (such as images, videos, stylesheets, and scripts) are loaded over an insecure HTTP connection”. Those subresource requests are open to on-path attackers, who can watch and modify what is sent.

Two categories, two different failure modes

  • Passive mixed content — images, video, audio. The risk is lower, but web.dev notes most browsers still report the page as insecure “even when the page itself is loaded over HTTPS”. Chrome automatically upgrades passive mixed content, loading the HTTPS copy of the asset; “if there's no secure version, the asset doesn't load”. Broken hero images are usually this.
  • Active mixed content — scripts, stylesheets, iframes, anything the browser can execute. “Most browsers already block this type of content by default.” The result is silent: the map never renders, the form never submits, the widget simply does nothing.

Chrome lists every insecure resource and its restriction status in the DevTools Issues tab, which is the fastest way to see the real list rather than the visible symptoms.

How this became a commercial problem

Chrome has marked all HTTP pages “Not secure” in the address bar since Chrome 68 (July 2018), and escalated from Chrome 70 (October 2018) to a red warning when someone enters data on an HTTP page. HTTPS has also been a ranking signal since 2014, though Google's own framing is worth keeping honest: “a very lightweight signal — affecting fewer than 1% of global queries”. The larger cost is behavioural. A security warning over a quote form or a checkout button ends the visit before rankings matter.

The fix order that clears it

  1. Serve everything over HTTPS. A valid certificate covering every hostname you actually use — with and without www. Let's Encrypt issues these at no cost, and auto-renewal plus expiry monitoring matters more than the certificate itself: an expired cert produces a full-page interstitial that is far more damaging than a mixed-content label.
  2. One 301 redirect from HTTP to HTTPS, and from any duplicate hostname, straight to the final URL with no chain through a third address.
  3. Sweep hard-coded http:// subresources. Template partials, header and footer embeds, legacy map or booking iframes, font and CDN URLs, leftover script tags, and form action attributes carried over from a pre-HTTPS theme.
  4. Align the URL surfaces. Internal links, canonical tags, og:url and sitemap.xml should all be HTTPS so crawl signals agree with what the browser loads.
  5. Add HSTS last, once nothing on the site depends on HTTP, so the browser stops attempting an insecure request at all.

The check is mechanical: search the rendered source for http://, open the DevTools Issues panel on the pages that carry forms, maps and embeds, then rescan after deployment. Mixed-content regressions almost always arrive the day someone pastes a new embed.
